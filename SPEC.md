# Техническая спецификация и форматы данных: Поисковая система захоронений Москвы (`data.mos.ru/opendata/64023`)

## 1. Назначение системы и целевые показатели

Кроссплатформенная локальная поисковая система (терминальный CLI, локальный веб-интерфейс и автономные десктопные сборки) предназначена для потоковой индексации, идемпотентного слияния и мгновенного полнотекстового поиска по выгрузкам реестра захоронений Москвы (набор открытых данных **64023** портала Правительства Москвы `data.mos.ru` — *«Поиск захоронений на территории города Москва» / реестр мест захоронений ГБУ «Ритуал»*) в официальных форматах `XLSX`, `CSV`, `JSON` и `XML`.

### Целевые нефункциональные показатели
- **Масштабируемость**: от сотен тысяч до **6 млн участков (~15–18 млн надписей)** без деградации времени отклика.
- **Холодный старт CLI**: **`< 10 мс`** (без загрузки базы данных в оперативную память).
- **Потребление RAM**: константный объём памяти при потоковом импорте.
- **Целевые платформы**:
  - **Windows** (`7 SP1 / 8.1 / 10 / 11 x64`, автономная portable-сборка `Захоронения Москвы.exe`);
  - **macOS** (`10.15 Catalina+` на Intel, `11.0+` на Apple Silicon; бандл `universal2` `Захоронения Москвы.app` с ad-hoc подписью, без Developer ID и нотаризации);
  - **Linux** (любой дистрибутив с `Python 3.8+`, запуск в один клик через `./run.sh` или сборку PyInstaller).

## 2. Спецификация официальных форматов данных набора `64023`

### 2.1. Каноническая схема записи участка захоронения
Одна запись набора данных `64023` описывает **одно место захоронения** (земельный участок или колумбарную нишу) и содержит следующие атрибуты:

| Системное имя поля | Русское наименование в шапке | Тип и формат значений |
| :--- | :--- | :--- |
| **`global_id`** | `global_id` | Уникальный целочисленный идентификатор карточки участка на портале `data.mos.ru` (10-значное число, например `2606331479`). В официальных выгрузках записи отсортированы по возрастанию `global_id`. |
| **`Cemetery`** | `Кладбище` | Наименование кладбища из справочника ГБУ «Ритуал» (см. раздел 2.4). |
| **`PlaceNumber`** | `Номер места (участка) захоронения` | Структурированный шифр места захоронения, разделённый `/` (см. раздел 2.3). В некоторых гео-выгрузках может отсутствовать (`NULL` / пустая строка). |
| **`GraveType`** | `Тип захоронения на участке` | Одно из трёх значений:<br>• `"гробом в землю"` (код `1`)<br>• `"урной в открытый колумбарий"` (код `2`)<br>• `"урной в землю"` (код `3`) |
| **`HasTombstone`** | `Наличие надмогильного сооружения` | `"да"` (`1`) или `"нет"` (`0`). При `"нет"` поле `Inscription` пустое. |
| **`Inscription`** | `Надпись на надмогильном сооружении` | Список надписей на памятнике (от `0` до `N` строк вида `<ФИО>[,<ТокеныДат>]`, подробная грамматика в разделе 2.5). |
| **`geoData`** | `geoData` | Пространственная геометрия участка (`Polygon` или `MultiPolygon` в координатах WGS84 `[lon, lat]`). Позволяет вычислить центроид участка и площадь ограды в $\text{м}^2$. |
| **`geodata_center`** | `geodata_center` | Точка центра участка (`Point` в координатах WGS84 `[lon, lat]`). |

### 2.2. Особенности физических форматов выгрузок `data.mos.ru`

1. **Табличный формат `XLSX` (OOXML Spreadsheet, генератор `Apache POI`)**:
   - Архив ZIP содержит метаданные `docProps/core.xml` с точной датой формирования выгрузки в теге `<dcterms:created>` (тогда как в имени файла полного среза на портале часто стоит дата-заглушка `2999-01-01`).
   - Таблица общих строк `xl/sharedStrings.xml` в выгрузках `Apache POI` обычно пуста (`count="0"`), а все ячейки в `xl/worksheets/sheet1.xml` записаны инлайн с типом `t="inlineStr"` (`<c r="A3" s="1" t="inlineStr"><is><t>...</t></is></c>`). Парсер поддерживает как `inlineStr`, так и стандартную таблицу `sharedStrings` (`t="s"`).
   - **Критическая особенность `Apache POI`**: в начале `xl/worksheets/sheet1.xml` записан некорректный тег размерности `<dimension ref="A1"/>` вместо реального диапазона строк. Парсер обязан игнорировать `<dimension>` и читать все теги `<row>` потоково через `zipfile` + `xml.etree.ElementTree.iterparse` с периодической очисткой обработанных XML-узлов.
   - Строка 1 содержит системные английские имена колонок (`PlaceNumber`, `GraveType`, `HasTombstone`, `Inscription`, `Cemetery`, `global_id`, опционально `geoData`, `geodata_center`), строка 2 — русские подписи колонок, строки `3..N` — данные участков.
   - Если в таблице присутствуют колонки `geoData` / `geodata_center`, `Apache POI` сериализует их в нестандартную строку Java-словаря без кавычек вокруг ключей:
     ```text
     {coordinates=[[[37.646255936, 55.817816769], ...]], type=Polygon}
     ```

2. **Табличный формат `CSV`**:
   - Кодировка `UTF-8` (с BOM или без), `Windows-1251` (`cp1251`) или `UTF-16`; разделитель полей — точка с запятой `;` (реже `,` или `\t`), экранирование кавычками `"`.
   - Первые две строки могут содержать системные и русские заголовки колонок (либо только русские заголовки на первой строке).
   - Внутри колонки `Inscription` в кавычках присутствуют многострочные переносы `\n\n`, поэтому разбор должен выполняться потоковым `csv.reader`, а не построчным `readline()`.

3. **Иерархический формат `JSON`**:
   - Встречается в двух официальных вариантах структуры объектов:
     - *Прямая выгрузка портала*: массив плоских объектов `[{"global_id": 2606331479, "PlaceNumber": "...", "GraveType": "...", "HasTombstone": "да", "Inscription": [{"Inscription": "..."}], "Cemetery": "...", "geoData": {"type": "Polygon", "coordinates": [...]}, "geodata_center": {"type": "Point", "coordinates": [lon, lat]}}, ...]`.
     - *Выгрузка через API (`apidata.mos.ru/v1/datasets/64023/rows`)*: массив объектов с обёрткой `[{"global_id": 2606331479, "Number": 1, "Cells": { ...атрибуты участка... }}, ...]`.
   - Поле `Inscription` в JSON представлено вложенным массивом объектов `[{"Inscription": "<строка>"}]` (либо массивом строк или единой мультистрокой с `Inscription:...\n\n`).

4. **Иерархический формат `XML`**:
   - Повторяющиеся элементы участков (обычно `<row>`, `<item>` или `<Element>`; имя тега не проверяется — записью считается любой элемент, у которого есть дочерние `<global_id>` и `<Cemetery>`), содержащие дочерние теги `<global_id>`, `<Cemetery>`, `<PlaceNumber>`, `<GraveType>`, `<HasTombstone>`, `<Inscription>`, `<geoData>`, `<geodata_center>`. Если среди первых `5000` XML-элементов не найдено ни одной такой записи, файл отклоняется.

### 2.3. Грамматика шифра места захоронения (`PlaceNumber`)
Шифр состоит из сегментов, разделённых символом `/`:
- **1-й сегмент** — буквенный префикс категории места (9 вариантов).
- **2-й сегмент** — 3-значный код кладбища (`002`..`154`).
- Остальные сегменты кодируют номер участка/квартала (или номер колумбария, секцию, сторону, ярус) и номер могилы/ниши:

| Префикс | Категория (`GraveType`) | Число сегментов | Структура и пример | Выделяемый `plot_section` |
| :--- | :--- | :---: | :--- | :--- |
| **`ЗИ`** | Земельный участок (`гробом в землю` / `урной в землю`) | 4 (или 5, если в номере участка есть `/`) | `ЗИ/<КодКладбища>/<Участок>/<Место>`<br>Пример: `ЗИ/002/3.3/1667`, `ЗИ/016/14/2/0105` | `"3.3"`, `"14/2"` (все сегменты между кодом кладбища и последним сегментом места) |
| **`СП`** | Семейное (родовое) захоронение | 4 | `СП/<КодКладбища>/<Участок>/<Место>`<br>Пример: `СП/002/4.1/0339` | `"4.1"` |
| **`НЗИ`** | Земельный участок | 4 | `НЗИ/085/1/2405` | `"1"` |
| **`РД`** | Участок по разрешению ДТиУ | 4 | `РД/002/3.3/1744` | `"3.3"` |
| **`ОУ`** | Особый участок | 4 | `ОУ/116/29/0001` | `"29"` |
| **`КО`** | Открытый колумбарий (`урной в открытый колумбарий`) | 7 или 8 | `КО/<КодКладбища>/<Колумбарий>/<Секция>/<Сторона>/<Ярус>/<Ниша>`<br>Пример: `КО/078/0002/24/3/3/13` | `"0002"` (3-й сегмент — номер колумбария) |

| **`КЗ`** | Закрытый колумбарий | 7 | `КЗ/016/0001/33/3/22/129` | `"0001"` |
| **`К`** | Колумбарная стена | 5 | `К/013/2668/4761/049` | `"2668"` |

### 2.5. Грамматика поля `Inscription` и алгоритм разбора надписей
1. **Сериализация в табличных форматах (`XLSX`, `CSV`)**:
   Ячейка `Inscription` содержит от `1` до `N` блоков, разделённых двойным переводом строки `\n\n`. Каждый блок начинается с префикса `Inscription:`:
   ```text
   Inscription:<строка_1>\n\nInscription:<строка_2>\n\n
   ```
2. **Структура одной строки надписи (`<строка_i>`)**:
   Строка состоит из текста надписи (обычно ФИО) и необязательных токенов дат (рождения и/или смерти), перечисленных через запятую без пробела:
   ```text
   <ФИО или текст>[,<ТокенДаты_1>,...,<ТокенДаты_k>]
   ```
   Каждая логическая дата представлена **одним** или **двумя** токенами из закрытого перечня примитивов (`DATE_TOKEN_RE = r"^(?:\d{2}\.\d{2}\.\d{4}|год\s*[\d*]+|месяц\s+\d{2}|день\s+\d{2})$"`):
   - Полная дата (`1` токен): `DD.MM.YYYY` (например, `16.03.1954`)
   - Только год (`1` токен): `год YYYY` (например, `год 1898`) или частично нечитаемый год со звёздочками `год **28`
   - Месяц и год (`2` токена): `месяц MM,год YYYY` (например, `месяц 07,год 1896`)
   - День и месяц (`2` токена): `день DD,месяц MM` (например, `день 16,месяц 08`)
   - День и год (`2` токена): `день DD,год YYYY` (например, `день 17,год 2004`)
   - Только день или только месяц (`1` токен): `день DD` или `месяц MM`
3. **Краевые случаи и обязательный разбор справа налево**:
   - **Запятые внутри ФИО**: в исходных данных встречаются двойные запятые после инициалов (`Ларькина С.М,,год 1919,год 1998`), запятые вместо точки между инициалами (`Попов И,А.,год 1931,год 1987`), запятые внутри пояснений в скобках (`Чернов Т. Т.(Сергей, сын),30.09.1931,17.03.1992`) и запятые в номерах разрешений (`Участок по разрешению ДТиУ №РД/002/3,2,2/0002`).
   - **Правило парсера**: строка разбивается по `,`, после чего токены дат отщепляются **строго справа налево**, пока очередной правый токен удовлетворяет `DATE_TOKEN_RE`. Все оставшиеся слева части склеиваются обратно через `,` в исходную строку ФИО.
   - **Группировка токенов дат**: отщеплённые токены дат группируются слева направо в логические даты по возрастанию ранга единицы времени (`день` < `месяц` < `год`). Если получена **1 логическая дата** (~5,3% записей, например `Щукина Людмила Александровна,16.03.1954`), она сохраняется в `single_date_raw` / `single_date_year`; если **2 и более** — первая сохраняется как дата рождения (`birth_date_raw` / `birth_year`), вторая — как дата смерти (`death_date_raw` / `death_year`).
   - **Пустое ФИО**: если строка начинается с запятой (`,день 16,месяц 08,12.11.2018`), `fio_norm` остаётся пустым, а при отображении подставляется `"ФИО не указано"`.
   - **Регистронезависимая префиксная дедупликация на участке**: в табличных выгрузках на одном участке часто соседствуют неполная и полная записи одного и того же человека (`Щукина Людмила Александровна,16.03.1954` и `Щукина Людмила Александровна,16.03.1954,18.12.2015`) либо дубль прописными буквами (`ЧЕМАГИН ЮРИЙ КОНСТАНТИНОВИЧ,23.08.1940`). Функция `deduplicate_inscriptions()` удаляет строку $A$, если она (после приведения к нижнему регистру и замены `ё → е`) является префиксом другой строки $B$ того же участка, а при точном регистронезависимом совпадении предпочитает смешанный регистр строке `КАПСОМ`.

1. **Язык и зависимости ядра**:
   - Python `3.8+` (`from __future__ import annotations`), **0 внешних зависимостей** для ядра, CLI и веб-сервера (только стандартная библиотека Python: `sqlite3`, `zipfile`, `zlib`, `xml.etree.ElementTree`, `csv`, `json`, `re`, `hashlib`, `dataclasses`, `argparse`, `http.server`, `socketserver`, `urllib`, `webbrowser`, `threading`, `logging`, `functools`, `subprocess`, `ctypes`, `platform`).

   - `src/` — чистая бизнес-логика:
     - `models.py` — структуры данных (`dataclass`);
     - `parser.py` — разбор шифров `PlaceNumber`, надписей `Inscription`, геометрии `geoData` и генерация ссылок на карты;

     - `search.py` — поисковый движок `FTS5` (`unicode61`, `fts5vocab`, `trigram`) и фильтрация дат;
     - `web_app.py` — многопоточный HTTP-сервер, JSON API и раздача статики;
     - `diag.py` — ротируемое файловое логирование (`logs/app.log`), сборка диагностического архива `moscow-burials-diagnostic.zip` и аварийные диалоги ОС;
     - `src/static/` — фронтенд веб-интерфейса (`index.html`, `styles.css`, `app.js`, `coat_of_arms.svg`).
   - `scripts/` — CLI-обёртки (`cli.py`, `web.py`, `build.py`, `make_universal_python.py` — склейка интерпретатора `universal2` из сборок `x86_64` и `arm64`; вызовы `print` разрешены только здесь).
   - `assets/` — ресурсы сборки: `AppIcon.ico` (иконка Windows) и `dmg-background.svg` (фон окна DMG).
   - `tests/` — модульные и интеграционные тесты (`test_core.py`).
   - `run.sh` — скрипт запуска веб-интерфейса в один клик для Linux и macOS.
   - `input/` — папка входных файлов-источников (`.xlsx`, `.json`, `.csv`, `.xml`).
   - `output/` — сгенерированная база данных (по умолчанию `output/burials.db`; база со старым именем `graves.db` при запуске переименовывается автоматически).
   - `logs/` — журнал работы `app.log` и диагностический архив `moscow-burials-diagnostic.zip`.
   - `tmp/` — временные рабочие артефакты и промежуточные файлы сборки PyInstaller.
   - `dist/` — готовые сборки (`.app`, папка с `.exe`, архивы `.zip` и образы `.dmg`).

## 4. Схема базы данных (`SQLite`)

### 4.1. Реляционные таблицы
1. **`cemeteries`** (справочник кладбищ):
   - `id INTEGER PRIMARY KEY`
   - `code TEXT` (3-значный код из `PlaceNumber`, например `"002"`; может быть `NULL`)
   - `name TEXT NOT NULL UNIQUE`
2. **`plots`** (места захоронений — 1 запись на `global_id`):
   - `global_id INTEGER PRIMARY KEY` *(алиас `rowid` для выборки за `< 0.1 мс`)*
   - `cemetery_id INTEGER NOT NULL REFERENCES cemeteries(id)`
   - `place_number TEXT` *(полный шифр `ЗИ/002/3.3/1667` или `NULL`)*
   - `plot_section TEXT` *(выделенный номер участка/колумбария, например `"3.3"`)*
   - `grave_type INTEGER NOT NULL` (`1` = гробом в землю, `2` = урной в открытый колумбарий, `3` = урной в землю)
   - `has_tombstone INTEGER NOT NULL` (`1` = да, `0` = нет)
   - `person_count INTEGER NOT NULL DEFAULT 0`
   - `lon REAL`, `lat REAL`, `area REAL` *(координаты центроида WGS84 и площадь полигона в $\text{м}^2$ из `geoData` / `geodata_center`)*
   - `source_date TEXT` *(дата актуальности среза `YYYY-MM-DD`, из которого получены текущие надписи участка)*
   > **Примечание**: внешние ссылки на карты в БД не хранятся — они детерминированно вычисляются при выдаче:
   > - Схема кладбища (`epoisk_map_url`): `https://epoisk.ru/burmsk/cemetery/{slug}/map/?gid={global_id}`
   > - Яндекс.Карты (`ya_url`): `https://yandex.ru/maps/?ll={lon}%2C{lat}&lang=ru&mode=search&text={lat}%2C{lon}&z=17`
   > - Google Maps (`google_url`): `https://www.google.com/maps?q={lat},{lon}&ll={lat},{lon}&z=18`
   > - OpenStreetMap (`osm_url`): `https://www.openstreetmap.org/?mlat={lat}&mlon={lon}#map=19/{lat}/{lon}`
   > - nakarte.me (`nakarte_url`): `https://nakarte.me/#m=18/{lat}/{lon}&l=I` (слой Bing Satellite)
3. **`persons`** (надписи на памятнике — 1 запись на человека/надпись):
   - `id INTEGER PRIMARY KEY`
   - `global_id INTEGER NOT NULL REFERENCES plots(global_id)`
   - `raw_line TEXT NOT NULL` *(исходная строка надписи без префикса `Inscription:`)*
   - `surname TEXT`, `firstname TEXT`, `patronymic TEXT` *(1-е, 2-е и 3-е слова ФИО в нижнем регистре с заменой `ё → е`)*
   - `fio_norm TEXT NOT NULL` *(полный нормализованный текст надписи без дат)*
   - `birth_year INTEGER`, `birth_date_raw TEXT`
   - `death_year INTEGER`, `death_date_raw TEXT`
   - `single_date_year INTEGER`, `single_date_raw TEXT`
4. **`import_history`** (журнал импортированных файлов-источников):
   - `id INTEGER PRIMARY KEY AUTOINCREMENT`
   - `sha256 TEXT NOT NULL UNIQUE`, `file_name TEXT NOT NULL`, `file_size INTEGER NOT NULL`
   - `source_date TEXT`, `imported_at TEXT NOT NULL`
   - `plots_seen INTEGER`, `persons_seen INTEGER`, `plots_inserted INTEGER`, `plots_updated INTEGER`, `persons_inserted INTEGER`

### 4.2. Индексы и виртуальные таблицы `FTS5`

## 5. Валидация входных данных и правила слияния (`src/importer.py`)

### 5.1. Двухфазная валидация файлов (`DataValidationError`)
1. **Фаза 1 (`validate_source_file`) — быстрая проверка до старта импорта**:
   - Проверка существования и непустоты файла (отклонение файлов `0` байт или состоящих только из пробелов/BOM).
   - Распознавание по магическим байтам и расширению неподдерживаемых архивов (`.rar`, `.7z`, `.gz`, а также нераспакованных `.zip` с выгрузкой внутри), старого бинарного формата Excel 97–2003 (`.xls` / OLE2), документов `.pdf` и сохранённых веб-страниц `.html` (даже если они переименованы в `.xlsx` или `.csv`).
   - Проверка целостности ZIP-контейнера `.xlsx` и наличия в нём листов `xl/worksheets/sheet*.xml`.
2. **Фаза 2 — потоковая проверка схемы и атомарность транзакции**:
   - В `XLSX` и `CSV`: проверка наличия обязательной колонки `global_id` в первых двух непустых строках (с поддержкой русских названий колонок через `RU_HEADER_ALIASES`), отклонение файлов с нулевыми байтами `\x00`.
   - В `JSON`: проверка наличия поля `global_id` (на верхнем уровне или внутри `Cells`) и контроль закрытия корневого JSON-массива `]` (защита от оборванных при скачивании файлов).
   - В `XML`: проверка наличия дочерних тегов `global_id` и `Cemetery`, перехват `ET.ParseError` при обрыве XML-потока.
   - **Атомарность**: весь импорт файла (запись данных, перестроение FTS-индексов `persons_fts` и `persons_trigram`, запись в `import_history`) выполняется в рамках одной транзакции SQLite (`open_import_db`) с единственным `COMMIT` в самом конце. При любой ошибке чтения или валидации в середине файла (или при `plots_seen == 0`) транзакция полностью откатывается (`ROLLBACK`), существующие данные в БД и `import_history` остаются нетронутыми, а невалидный файл, загруженный через браузер, автоматически удаляется, не засоряя папку `input/`.

### 5.1.1. Этапы импорта и его отмена
- Фоновый импорт проходит этапы (`phase`) `uploading` (только для файла, загружаемого через браузер) → `hashing` (подсчёт SHA-256) → `reading` (потоковое чтение и `UPSERT`) → `indexing` (перестроение FTS-индексов в 2 шага: «индекс по словам» `persons_fts`, «индекс по фрагментам слов» `persons_trigram`) и завершается состоянием `done`, `error` или `cancelled`.
- На этапах `hashing`, `reading` и `indexing` импорт можно остановить (`POST /api/import/cancel`, кнопка **«Остановить импорт»**). Отмена передаётся через потокобезопасный `ImportCancelToken`: флаг проверяется между блоками при хешировании, между записями при чтении и через SQLite progress handler каждые `100 000` инструкций виртуальной машины, поэтому даже многоминутное перестроение FTS-индекса прерывается почти сразу. Остановленный импорт завершается `ImportCancelledError` и полным откатом транзакции — база остаётся ровно такой, какой была до импорта.
- `GET /api/import/status` досчитывает время до текущего момента (`elapsed_sec`, `phase_elapsed_sec`, `step_elapsed_sec`), чтобы таймер в интерфейсе не застывал на долгих шагах без обновлений прогресса.

### 5.2. Идемпотентное слияние («Свежесть + Полнота»)
- Дата актуальности файла (`source_date`) определяется автоматически из `docProps/core.xml` внутри `.xlsx`, даты упаковки листа или имени файла (`ДД.ММ.ГГГГ` / `ГГГГ-ММ-ДД`, игнорируя заглушку `2999-01-01`), либо задаётся пользователем.
- При повторном или последовательном импорте разных срезов по одному и тому же `global_id`:
  - **Новый источник свежее (`new_date > old_date`)**: непустые атрибуты и список надписей из нового файла обновляют запись, а отсутствующие в новом срезе поля (например, `place_number`, если в новом файле он пуст, или `lon`/`lat`/`area`, если в новом файле нет `geoData`) сохраняются из старой записи.
  - **Новый источник старше (`new_date < old_date`)**: старый архивный срез **не перезаписывает** более свежие надписи, а только дозаполняет пустые (`NULL`) поля участка.
  - **Даты равны или не указаны**: списки надписей объединяются через регистронезависимую префиксную дедупликацию `deduplicate_inscriptions()`.

## 6. Правила поиска (`src/search.py`)

### 6.1. Синтаксис запроса ФИО (совместимый с `epoisk.ru/burmsk/`)
1. **Автоматическое сведение родовых окончаний фамилий (`_strip_flexion`)**:
   - Мужские и женские окончания фамилий в именительном падеже (`-ий/-ый/-ой/-ая/-яя` и `-ова/-ева/-ина/-ына`) автоматически приводятся к общей основе: запрос `Красновский` находит и `Красновский`, и `Красновская`; запрос `Соколова` находит и `Соколова`, и `Соколов`. Личные имена (`Евгений`, `Дмитрий`, `Галина`, `Марина`, `Мария`, `Илья`) и несклоняемые фамилии (`Шевченко`, `Дюма`) не урезаются.
2. **Специальные операторы**:
   - **Двойные кавычки `"..."`** — точная словоформа без отсечения окончаний (`"Красновский"` найдёт только мужскую форму).
   - **Точка `.` после инициала (`Е. Я.`)** — строгое совпадение однобуквенного инициала на памятнике (в отличие от `Е Я` без точек, которое находит любые имена и отчества на `Е...` и `Я...`).
   - **Символ `$` в конце слова (`Иван$`)** — фиксация конца слова (найдёт `Иван`, но не `Иванов` и не `Ивана`).
   - **Оператор `~` (`0` или `1` любой символ)** — `Куз~миченков` находит и `Кузмиченков`, и `Кузьмиченков`; `Иван~$` находит `Иван` и `Ивана`, но не `Иванов`.
   - **Оператор `?` (ровно `1` любой символ)** — `Натал?я` находит `Наталья` и `Наталия`.
   - **Оператор `*` (`0` или более любых символов)** — произвольный суффикс/подстрока, включая дефисные фамилии (`Соколов-Микитов*`).
   - **Оператор `|` (логическое ИЛИ внутри позиции слова)** — `Елена|Алена`.
3. **Режимы поиска (`search_mode`)**:
   - `prefix_default` (по умолчанию): 1-е слово ищется в `surname`, 2-е (если всего 2 слова) — в `{firstname patronymic}`, при 3 словах — 2-е в `firstname`, 3-е в `patronymic`.
   - `prefix_no_surname`: все слова запроса ищутся по началам слов в любом месте `fio_norm`.
   - `substring`: поиск вхождений в середине слов через триграммный индекс `persons_trigram`.

### 6.2. Фильтрация по датам и совместным захоронениям (`ФИО1 + ФИО2`)
- Поля `birth_exact` и `death_exact` принимают точный год (`1954`), месяц и год (`03.1954`), полную дату (`16.03.1954`), а также закрытые и открытые диапазоны через дефис (`1900-1967`, `1900-12.12.1967`, `02.1967-10.1967`, `1900-`, `-1967`).
- При поиске по диапазону с точностью до дня или месяца записи памятников, на которых выбит только год (`год YYYY`), автоматически включаются в выборку, если их год попадает в диапазон.
- Если задан фильтр второго человека (`person2`), CTE группирует совпадения `m1` и `m2` по `global_id` за $O(N)$ и возвращает участки, где захоронены минимум два разных человека (`m1.only_pid IS NULL OR m1.only_pid != m2.only_pid`).

## 7. Интерфейсы, диагностика и десктопные дистрибутивы

1. **Терминальный CLI (`scripts/cli.py`)**:
   - `python -m scripts.cli import <paths...> [--db output/burials.db] [--source-date YYYY-MM-DD]`
   - `python -m scripts.cli search [ФИО] [флаги] [--json]`
   - `python -m scripts.cli clear [--db output/burials.db] [-y]`
   - При пути к базе по умолчанию CLI и веб-интерфейс перед работой переименовывают `graves.db` (имя в версии 0.1.0) в `burials.db` вместе со служебными файлами `-wal`, `-shm`, `-journal` (`migrate_legacy_db_file`); если переименовать не удалось (например, файл открыт другой копией программы), уже перенесённые файлы возвращаются на место и используется старое имя.
2. **Локальный веб-интерфейс (`scripts/web.py`, `src/web_app.py`)**:
   - Привязка к `127.0.0.1:64023` через `LocalLoopbackHTTPServer` (без `socket.getfqdn()`, что предотвращает системные запросы доступа к локальной сети на macOS).
   - Повторный запуск приложения при уже работающем сервере на порту `64023` открывает новую вкладку браузера и завершается с кодом `0`.
   - Многовкладочный heartbeat (`POST /api/heartbeat` раз в 60 с и `navigator.sendBeacon("/api/client/close")` при закрытии вкладки): сервер автоматически выключается через **10 минут (`600` с)** после закрытия последней вкладки (если не идёт импорт) либо мгновенно по кнопке **«Выход»** (`POST /api/shutdown`).
   - Флаги запуска: `--db`, `--host`, `--port`, `--no-browser`, `--diag`.
   - Основные маршруты JSON API: `GET /api/meta`, `/api/sources`, `/api/search`, `/api/import/status`; `POST /api/import/start`, `/api/import/upload`, `/api/import/cancel`, `/api/import/dismiss`, `/api/db/clear`, `/api/open-input-dir`.
   - Экспорт результатов поиска (`GET /api/export.csv`) отдаётся файлом `burials-export-ГГГГ-ММ-ДД_ЧЧ-ММ-СС.csv` (локальное время сервера).
3. **Диагностическое логирование (`src/diag.py`, папка `logs/`)**:
   - Ротируемый лог `logs/app.log` (`1 МБ × 2` файла, `UTF-8`), фиксирующий паспорт окружения при старте, все стадии импорта, поисковые запросы, а также JS-ошибки из браузера (`POST /api/client/error`).
   - Автоматическая упаковка диагностического архива `logs/moscow-burials-diagnostic.zip` (содержащего `diagnostic_info.json`, `app.log`, `app.log.1`) по завершении фонового импорта, при штатной остановке сервера, при фатальной ошибке старта (с нативным окном ошибки ОС и открытием папки), по флагу `--diag` и по кнопкам веб-интерфейса **«Скачать лог (.zip)»** (`GET /api/log.zip`) и **«Показать лог в папке»** (`POST /api/open-log-dir`).
4. **Сборка дистрибутивов (`scripts/build.py`)**:
   - PyInstaller собирает приложение только для той ОС, в которой запущен (Windows-сборку можно выполнить под Wine на macOS / Linux). Общие флаги: `--zip` — архив `dist/moscow-burials-<версия>-<macos|windows|linux>-<архитектура>.zip` (`windows-x64`, `linux-x86_64`, `macos-universal`) с одним только приложением (версия из `src/__init__.py`); `--include-db` (и `--db <путь>`) — положить готовую базу внутрь дистрибутива; `--name` — другое имя выходного приложения.
   - **macOS (`dist/Захоронения Москвы.app`)**: генерация `AppIcon.icns`, `LSMinimumSystemVersion = 10.15.0` (ниже нельзя: сборка ведётся на переносимом Python 3.14 из python-build-standalone, которому нужна macOS 10.15+), `--target-arch` (`x86_64` по умолчанию — на Apple Silicon запускается через Rosetta 2, `arm64`, `universal2` — релизный вариант; для universal2 интерпретатор склеивается `scripts/make_universal_python.py`), ad-hoc подпись `codesign`, проверка архитектуры и `minos` у всех Mach-O файлов бандла (`10.15` для `x86_64`, `11.0` для `arm64`; сборка падает при несоответствии), флаг `--dmg` — релизный образ `dist/moscow-burials-<версия>-macos-<universal|x86_64|arm64>.dmg` через `dmgbuild` (HFS+, ULMO; окно 640×400 с фоном `assets/dmg-background.svg` в 1x/@2x, ярлык «Программы» на `/Applications`, иконка тома; проверка `hdiutil verify` и `codesign --verify` внутри образа; после упаковки `.app` из `dist/` удаляется); рабочие папки (`output/burials.db`, `input/`, `tmp/`, `logs/`) располагаются в `~/Library/Application Support/moscow-burials/`.
   - **Windows (`dist/Захоронения Москвы/Захоронения Москвы.exe`)**: сборка на Windows Python 3.8.10 x64 (совместимость с Windows 7 SP1 / 8.1 / 10 / 11 x64), мультиразмерная иконка `assets/AppIcon.ico` (хранится в репозитории; её обновляет сборка на macOS, сборке на Windows она нужна готовой); рабочие папки располагаются portable рядом с `.exe` (с автоматическим откатом в `%LOCALAPPDATA%\moscow-burials` при отсутствии прав записи).
   - **Linux (`./run.sh`)**: запуск в один клик на системном `python3` (для frozen-сборки — portable-папка или `$XDG_DATA_HOME/moscow-burials`).
